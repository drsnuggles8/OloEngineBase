# Gaussian splats stay an offline import behind a prototype renderer; they do not become a runtime asset type until the per-view sort moves off the CPU

Issue [#971](https://github.com/drsnuggles8/OloEngineBase/issues/971) asked for a constrained
viability spike, not a feature. This is its decision record: what was built, what it measured, what
a splat cloud does and does not interact with in this engine, and the one number that decides
whether the feature is affordable.

**The decision, up front.** OloEngine can render 3D Gaussian splats correctly — the prototype in
this PR does — and the representation is dramatically cheaper in memory than the source PLY. It
does **not** become a supported asset type now. The blocker is not fidelity and it is not fill
rate: it is that correct compositing needs the whole visible cloud re-sorted from the eye **every
frame**, and on the CPU that cost is linear in cloud size and lands in the frame budget. Reopen
when the sort is a GPU pass. Everything else on the list (shadows, collision, probes, scene
serialization) is a deliberate "does not interact", stated in §4 rather than left to be discovered.

The spike was timeboxed to one working session. What follows is what fit.

## 2. Source format and asset representation

The source is the PLY the INRIA 3DGS trainer writes and every viewer reads: one `vertex` element
with 62 float properties per splat — `x y z`, `nx ny nz`, `f_dc_0..2`, `f_rest_0..44`, `opacity`,
`scale_0..2`, `rot_0..3`. 248 bytes per splat.

Three decode rules, each a place where a wrong constant produces a cloud that renders and is wrong:
`opacity` is a **logit** (sigmoid on load), `scale_*` is a **logarithm** (exp on load), `rot_*` is a
quaternion stored **`w x y z`** and not normalised on write. `f_dc_*` is the band-0 spherical
harmonic: colour is `0.5 + 0.28209479 * f_dc`. Every one of those is pinned in
`GaussianSplatPipelineTest` against the fixture generator's own inputs, because a screenshot cannot
tell a correct decode from a quaternion read one component out — both look like a cloud of blobs.

**Properties are matched by NAME, never by offset.** Exporters disagree about whether `f_rest_*` is
present at all and about block order; a by-offset reader turns that disagreement into a
plausible-looking wrong cloud instead of an error.

The runtime record is 32 bytes:

```
vec3 Position          12 B
u32  ColorOpacity       4 B   RGBA8, alpha = opacity
u32  Cov{XXXY,XZYY,YZZZ} 12 B  upper triangle of the world covariance, six halves
u32  Pad0               4 B
```

The covariance `Sigma = R S S^T R^T` is baked at import: scale and rotation are never wanted
separately at draw time. The `f_rest_*` bands are **dropped**, which costs view-dependent colour
(specular highlights in a scan stop moving with the eye) and is the single largest memory saving
available — 45 of the 62 source floats.

One consequence of the packing is worth knowing before anyone reuses this record. A covariance term
is a squared length, and half's smallest *normal* is 6.1 × 10⁻⁵, so **every splat with a sigma below
about 7.8 mm stores its covariance as a denormal**, where precision stops scaling with the value.
That is most of a real metre-scale scan. It is survivable, because the error on the recovered sigma
is half the error on the stored term: measured, a splat is within 0.5 % of its authored size down to
sigma = 10 mm, within 2 % at 1 mm, and degrades to roughly 20 % at 0.25 mm.
`HalfCovarianceDegradesPredictablyForSmallSplats` pins those bounds. Storing scale and rotation
separately (as the reference implementations do) would avoid the squaring and is the obvious fix if
sub-millimetre detail ever matters.

## 3. Ordering, visibility and bounded LOD

A splat is a semi-transparent primitive, so the frame is only correct composited **back-to-front
from the current eye**. That makes the ordering a per-frame, per-view cost proportional to the
visible cloud — not a bake, and not something an acceleration structure removes.

`BuildViewOrdering` does, in one pass: alpha reject → near-plane reject (the projection diverges at
the eye plane, so there is no correct thing to draw there) → conservative frustum cull against the
splat's 3σ radius → **LOD**, dropping any splat whose 3σ footprint projects below a pixel
threshold → **budget**, an absolute ceiling on splats submitted, keeping the highest
screen-area × alpha and breaking ties on cloud index so the kept set does not flicker between
frames → radix sort.

The sort key is the **IEEE bit pattern of the positive view depth**. For strictly positive floats
that pattern is monotonic in the value, so a four-pass 8-bit radix over it is an exact float sort —
no quantisation, no depth range to choose, no bucket-boundary ties. Descending order comes from
complementing the keys, not from reversing the last pass's buckets: the last pass is usually
*skipped* as uniform (the top byte of a float depth is sign plus most of the exponent), and a
reversal implemented there silently returns ascending order in exactly that case.

`DrawOrderChangesTheImage` renders the same pose in the correct and the reversed order and asserts
the frames differ. Without it, the sort could be dead code and the suite would still be green.

## 4. The interaction contract

Most of this table is "does not interact". Writing that down is the point: an unstated contract is
how a research prototype becomes an unmaintainable feature.

| Surface | Today | Why, and what it would take |
|---|---|---|
| **Depth buffer** | Tested, never written. | A splat has no surface, so there is no depth to write. It can be depth-tested against the opaque G-buffer if drawn after opaque geometry — the prototype's `gl_Position.z` carries the real NDC depth for exactly that. Splats cannot occlude each other through depth; only the sort orders them. |
| **Deferred lighting** | Not integrated, and cannot be. | The colour in a splat is **baked radiance** from the capture, not a BRDF input. It has no normal, roughness or albedo to write into the G-buffer. A splat cloud must be composited *after* lighting, in the transparency phase. |
| **Shadows (cast)** | No. | Nothing to rasterise into a CSM or VSM page. Casting needs a separately authored opaque proxy mesh, which is a second asset with its own authoring cost. |
| **Shadows (receive)** | No, and it would be wrong. | The capture's own lighting is already in the colour. Applying engine shadows on top double-darkens. |
| **Reflection probes / IBL** | No. | The probe bake path renders meshes through the deferred pass; splats are not in it. And a splat receives no IBL, for the same baked-radiance reason. |
| **Collision (Jolt)** | No. | No surface, no triangles. A splat cloud is decoration; anything the player touches needs a proxy body. |
| **Scene serialization** | None. | This is the honest cost of "make it a feature": a `SplatCloudComponent` pulls in the whole cross-binding list in `CLAUDE.md` — `AllComponents`, save-game capture/restore *and* a hand-written `Serialize` overload, Lua registration, the editor inspector and Add Component menu, and a scene-YAML block (the component holds a `Ref<T>`, so codegen skips it). None of that exists and none of it should until the decision below flips. |
| **Asset registry** | Deliberately outside it. | `.ply` is **already** registered as `AssetType::MeshSource`, so a splat PLY dropped in the Content Browser today is read by assimp as a point mesh and silently loses everything but `x y z`. Two importers cannot share one extension; a real feature has to discriminate on file *content* (an `f_dc_0` property). See `notes-editor-and-assets.md`. |
| **OpenGL 4.6** | Works. This is what the evidence PNGs are. | |
| **Vulkan** | The shader compiles for `vulkan1.2`; the *binding model* does not port as written. | ADR 0010/0011: the Vulkan backend is heap-bindless only. The prototype binds two SSBOs and a UBO to fixed binding points, which is precisely the model that backend does not have. An RHI-neutral splat pass has to go through the neutral resource/binding-address model, and the sort output has to become a GPU buffer the heap can address. This is a real port, not a recompile. |

## 5. Measurements

All numbers below are from this workstation (RTX 4090, Windows 11, clang-cl) on 2026-09-03. They are
**not** CI gates — no assertion depends on any of them
(`oloengine-perf-tests-are-dev-workstation-only`). Re-derive before quoting them anywhere else.

### 5.1 Memory

| | 4,096-splat fixture | per splat |
|---|---|---|
| Source PLY (62 float properties) | 1,017,407 B | 248 B |
| Runtime GPU record | 131,072 B | 32 B |
| Dropped at import (`nx ny nz`, `f_rest_0..44`) | 786,432 B | 192 B |
| Draw-order buffer, rebuilt every frame | 16,264 B | 4 B |

**7.8× smaller than the source**, and that is the representation's one unambiguous win.
Extrapolated, a 2 M-splat scan is a 496 MB PLY that becomes 64 MB of GPU records plus up to 8 MB of
order indices per view. The ratio hides the fact that memory is also where a splat cloud is *worst*
against a mesh asset: a mesh shares one texture across thousands of triangles and streams by mip,
while splat memory is linear in captured detail with nothing to share and no mip chain to drop.

### 5.2 CPU — the per-view ordering pass

Release, single-threaded, 1280×720, the whole cloud in frame, mean of 20 iterations, median of three
runs on an otherwise idle machine. Measured with a standalone `-O2` probe over the same two
translation units, **not** the Debug test binary: the suite's own printed numbers are 5–10× higher
because `/MDd` checked iterators serialise every `std::vector` access, and quoting those would have
overstated the case by an order of magnitude.

| splats | drawn | whole pass | radix sort alone | `std::stable_sort` on the same keys |
|---:|---:|---:|---:|---:|
| 4,096 | 4,066 | **0.14 ms** | 0.027 | 0.021 |
| 100,000 | 99,208 | **2.60 ms** | 0.76 | 0.87 |
| 500,000 | 496,002 | **16.55 ms** | 4.94 | 5.43 |
| 2,000,000 | 1,048,576 (budget) | **155.3 ms** | 15.9 | 14.5 |

Two things fall out of that table, and both were surprises.

**The sort is not the expensive half — the per-splat cull and LOD are.** At 500 k the sort is about
5 ms of a 16.5 ms pass. The other 11 ms is one covariance unpack, one dot product, six plane tests
and a candidate push per splat, plus the allocation that collects them. That work is embarrassingly
parallel and is exactly what a compute dispatch is for. It is not evidence against splats; it is
evidence that this pass is running on the wrong processor.

**The radix sort is not measurably faster than `std::stable_sort`.** Across six runs the two traded
places at every size and the gap never left run-to-run noise — four passes of scattered 8-byte
writes over a multi-megabyte working set buy nothing over a cache-friendly merge. The radix
formulation is kept anyway, and the reason is stated rather than assumed: it is the one that ports
to a GPU sort, which is where this has to end up. A CPU-only implementation should use
`std::stable_sort` and delete the radix pass.

**The gate.** A 16.7 ms frame at 60 Hz has everything else in the engine in it too. Giving the
ordering pass a fifth of the frame — 3.3 ms, already generous for one feature — buys roughly
120–150 k visible splats on this machine, and the whole frame buys 500 k. Published 3DGS captures of
a single room are 1–6 M splats. That is the decision in one sentence: the cloud sizes people
actually publish are an order of magnitude past what this pass can order in a frame.

### 5.3 GPU — the splat pass against an opaque control

Measured with `GL_TIME_ELAPSED` in the Debug test binary (host build configuration does not change
GPU work), reported as the **minimum of four interleaved samples** per configuration. Both parts of
that matter and both come from a real mismeasurement here: A-then-B drifts far enough on this box to
invert a comparison, and a first run reported 10.3 ms where a later run reported 4.3 ms for the
identical draw, because the GPU had not reached its clock state. The control is
`SplatSpike_OpaqueBaseline.glsl`: the same instance count, the same quads at the same screen
positions and sizes, but depth-tested and opaque instead of sorted and blended.

| splats drawn | splat pass | opaque control | ratio |
|---:|---:|---:|---:|
| 4,066 | 0.025 ms | 0.010 ms | 2.5× |
| 99,208 | 0.752 ms | 0.417 ms | 1.8× |
| 496,002 | 6.285 ms | 3.480 ms | 1.8× |

The absolute times move by up to 2× between runs with GPU clock state; the **ratio** held at 1.8× at
both large sizes across three separate runs, so that is the number to trust. **Blending plus the
per-fragment Gaussian costs about 1.8× an equivalent opaque pass** — affordable. What is not
affordable is what both columns share: at 500 k splats the cloud covers the 1280×720 frame roughly
160 times over, and 6 ms of GPU time buys one 500 k-splat cloud and nothing else. Splat cost is
overdraw cost, and overdraw *grows* as the camera approaches — the opposite of a mesh, whose cost
falls as it leaves the frame.

### 5.4 Quality, and where the LOD knob fails

`Splat_Front.png`, `Splat_Corner.png`, `Splat_Top.png` and `Splat_Close.png` are the fixture from
four poses. They read correctly: the disc facing the camera is a filled ellipse while the two
edge-on discs are thin lines (so the anisotropic covariance survives the 32-byte packing), the three
discs cut each other along the right half-spaces, and the translucent shell composites over all of
them. `Splat_Corner_ReversedOrder.png` is the same pose drawn front-to-back — every occlusion
inverts, and the frame moves 3.9/255 mean absolute difference, which is what makes the sort's
necessity visible rather than asserted.

`Splat_Budget_4096/1024/256.png` are the LOD ceiling, and they are the spike's other negative
result. **The budget does not degrade gracefully.** Ranking survivors on screen-area × alpha keeps
the large opaque disc splats and deletes the faint shell. Measured on the Corner pose, cutting the
cloud to a quarter takes the shell from 103,956 painted pixels to 2,074 — a 98 % loss — while the
discs keep 41,200 of 49,288, or 84 %. At 256 splats what is left is a skeleton, not a lower-detail
scene. `TheSplatBudgetDropsTheDiffuseMassBeforeTheBrightDetail` asserts that asymmetry so it cannot
quietly change.

The reason generalises past this fixture. A splat cloud has no cheap LOD *by selection*, because one
splat's contribution is not separable from its neighbours' — dropping half the splats halves the
accumulated opacity of everything they were part of. LOD for splats means **merging**: fitting one
larger Gaussian to a group of small ones offline, so a coarse level still integrates to roughly the
same radiance. That is a build-time problem, and it is not in this spike.

## 6. Conclusion and follow-ups

**Proceed with constraints, and not yet.** Specifically:

1. **The importer and this prototype land** (this PR) as a documented spike: no scene integration,
   no component, no asset-registry entry, no production shader binding. It is reference material
   and a starting point, and it says so.
2. **Splats do not become a supported asset type** until the per-view ordering pass is something
   other than a single CPU thread. That is the one measurement that decides it (§5.2), and it is a
   precondition rather than a preference.
3. **The contract in §4 does not change quietly.** A future PR that gives a splat cloud shadows,
   collision or probe capture amends this ADR first.

A note on why this is not a flat "no". Nothing about the *quality* argued against splats: the frames
are correct from every pose tried, the runtime record is 7.8× smaller than the source, and the GPU
raster cost is within 2× of ordinary opaque geometry covering the same pixels. The blocker is one
pass on the wrong processor, and that is known, bounded work. A future session should reopen this
with numbers rather than re-litigate the format.

### Follow-ups

Filed and scored separately, because an unscored follow-up is invisible to the picker:

- **GPU per-view splat ordering** — move the cull, the LOD test, key generation and the sort into
  compute and drive the draw indirectly. This is the gate in §5.2, and `GPUPrefixSum` (#713) already
  supplies the scan a GPU radix sort needs.
- **Hierarchical splat LOD by merging** — an offline build step producing coarse levels whose splats
  integrate to roughly the same radiance, replacing the selection budget that §5.4 shows does not
  degrade gracefully.

Deliberately **not** filed: the `SplatCloudComponent` and its cross-binding touch-points, the
content-sniffing PLY import dispatch, and the RHI-neutral Vulkan pass. All three are real work and
all three are wasted until the two above land; filing them now would put them in front of the picker
as though they were startable.

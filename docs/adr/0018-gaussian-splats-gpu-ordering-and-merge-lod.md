# Gaussian splats order per view on the GPU and coarsen by merging; a CPU sort and a selection budget are both dead ends

Issue [#971](https://github.com/drsnuggles8/OloEngineBase/issues/971) asked for a constrained
viability spike. This is its decision record: what was built, what it measured, what a splat cloud
does and does not interact with in this engine, and the two numbers that decide whether the feature
is affordable.

**The decision, up front.** Gaussian splats are viable in OloEngine. Two things had to be true and
now are, both measured in this PR: the per-view ordering runs on the GPU
(**0.51 ms for 500 k splats, 4.7 ms for 2 M** — 33× the single-threaded CPU pass it replaces), and
LOD comes from **merging** splats offline rather than selecting among them at draw time. What is
*not* done, deliberately, is the integration: no component, no scene serialization, no asset-registry
entry, no Vulkan port. §4 states every interaction a splat cloud has and does not have, and §6 says
what remains.

**This ADR reversed its own conclusion inside one PR, and the honest version is worth keeping.** The
first draft said "do not proceed": the CPU ordering pass cost 16.6 ms at 500 k splats, a whole 60 Hz
frame, against published captures of 1–6 M splats. That was the right call on that evidence. Then
[#1038](https://github.com/drsnuggles8/OloEngineBase/issues/1038) and
[#1039](https://github.com/drsnuggles8/OloEngineBase/issues/1039) — the two preconditions it named —
were implemented, and the blocking number moved by a factor of 33. The measurement was the argument
in both directions.

## 2. Source format and asset representation

The source is the PLY the INRIA 3DGS trainer writes and every viewer reads: one `vertex` element
with 62 float properties per splat — `x y z`, `nx ny nz`, `f_dc_0..2`, `f_rest_0..44`, `opacity`,
`scale_0..2`, `rot_0..3`. 248 bytes per splat.

Three decode rules, each a place where a wrong constant produces a cloud that renders and is wrong:
`opacity` is a **logit** (sigmoid on load), `scale_*` is a **logarithm** (exp on load), `rot_*` is a
quaternion stored **`w x y z`** and not normalised on write. `f_dc_*` is the band-0 spherical
harmonic: colour is `0.5 + 0.28209479 * f_dc`. Every one is pinned in `GaussianSplatPipelineTest`
against the fixture generator's own inputs, because a screenshot cannot tell a correct decode from a
quaternion read one component out — both look like a cloud of blobs.

**Properties are matched by NAME, never by offset.** Exporters disagree about whether `f_rest_*` is
present at all and about block order; a by-offset reader turns that disagreement into a
plausible-looking wrong cloud instead of an error.

The runtime record is 32 bytes:

```
vec3 Position          12 B
u32  ColorOpacity       4 B   RGBA8, alpha = opacity
u32  Cov{XXXY,XZYY,YZZZ} 12 B  upper triangle of the world covariance, six halves
u32  Pad0               4 B
```

The covariance `Sigma = R S S^T R^T` is baked at import: scale and rotation are never wanted
separately at draw time. The `f_rest_*` bands are **dropped**, which costs view-dependent colour
(specular highlights in a scan stop moving with the eye) and is the single largest memory saving
available — 45 of the 62 source floats.

One consequence of the packing is worth knowing before anyone reuses this record. A covariance term
is a squared length, and half's smallest *normal* is 6.1 × 10⁻⁵, so **every splat with a sigma below
about 7.8 mm stores its covariance as a denormal**, where precision stops scaling with the value.
That is most of a real metre-scale scan. It is survivable, because the error on the recovered sigma
is half the error on the stored term: measured, a splat is within 0.5 % of its authored size down to
sigma = 10 mm, within 2 % at 1 mm, and degrades to roughly 20 % at 0.25 mm.
`HalfCovarianceDegradesPredictablyForSmallSplats` pins those bounds. Storing scale and rotation
separately (as the reference implementations do) would avoid the squaring and is the obvious fix if
sub-millimetre detail ever matters.

## 3. Ordering, visibility and LOD

A splat is a semi-transparent primitive, so the frame is only correct composited **back-to-front
from the current eye**. That makes the ordering a per-frame, per-view cost proportional to the
visible cloud — not a bake, and not something an acceleration structure removes. It is the central
cost of the whole technique.

### 3.1 The pass, on both processors

`BuildViewOrdering` (CPU) and `SplatSpike_Cull.comp` + `SplatSpike_BitonicSort.comp` (GPU) do the
same four things: alpha reject → near-plane reject (the projection diverges at the eye plane, so
there is no correct thing to draw there) → conservative frustum cull against the splat's 3σ radius →
**LOD**, dropping any splat whose 3σ footprint projects below a pixel threshold → sort far-to-near.

The CPU version stays as the **reference**, not as a fallback. `GaussianSplatGpuOrderingParityTest`
asserts the two agree *index for index and stat for stat* across four poses, eight splat counts
straddling the sort's padding boundary, and a cloud where every depth is bit-identical.

### 3.2 The sort key is a total order, which is what makes exact parity possible

The key is the **IEEE bit pattern of the positive view depth, complemented**. For strictly positive
floats that pattern is monotonic in the value, so an ascending integer sort over the complement is an
exact far-to-near float sort — no quantisation, no depth range to choose. Ties break on the **cloud
index**, which is unique, so the comparison is a *total* order: exactly one output permutation
satisfies it.

That single property buys three things at once, and it is the reason the GPU work is provable rather
than plausible:

* the CPU's stable radix sort and the GPU's unstable bitonic network produce the **same array**, so
  the parity test can assert equality instead of "same set, roughly ordered";
* the GPU cull can compact with an unordered atomic without becoming nondeterministic;
* two splats at the same depth cannot swap between frames, which is a shimmer the eye picks up.

On the CPU, descending order comes from complementing the keys and **not** from reversing the last
radix pass's buckets: that pass is usually skipped as uniform (the top byte of a float depth is sign
plus most of the exponent), and a reversal implemented there silently returns ascending order in
exactly that case.

### 3.3 Why the GPU sort is bitonic and not the radix #1038 proposed

#1038 proposed a four-pass LSD radix over `GPUPrefixSum` (#713). That is the faster algorithm and it
is what a production path should end up with. It is not what shipped, for one reason: a radix sort
only replaces the CPU reference if it is **stable**, and a stable GPU radix needs per-tile rank
computation — ballot-based, or a 256×256 shared histogram it cannot afford — which is easy to get
subtly wrong and hard to prove right. Bitonic sorting on the *pair* needs no stability at all
(§3.2), so the parity test can be exact. For a spike whose entire value is a trustworthy
measurement, a slower algorithm that is provably identical beat a faster one that is probably right.

The naive bitonic network is O(log²N) dispatches — 231 for 2²¹ elements, each re-reading the whole
array. Every step whose stride is below a workgroup's 512-element tile is instead resolved in shared
memory, which takes that to 21 global plus 21 local. The measured dispatch count for the 4096-splat
fixture is 1 cull + 6 global + 12 local = **19**, and `TheIndirectDrawCountIsWrittenByTheGpu` pins it
so a regression to one-dispatch-per-step cannot pass unnoticed.

### 3.4 LOD is merging, not selection

The spike's first LOD knob was a **budget**: rank survivors by projected area × alpha, keep the top
N. It caps frame cost and it destroys the picture, because one splat's contribution is not separable
from its neighbours' — dropping half the splats in a region halves the accumulated opacity of
everything they were part of. §5.5 has the measurement.

`SplatLodChain` builds coarse levels offline instead. Splats are clustered by recursive median split
on the widest axis (deterministic, with the cloud index breaking ties so a plane of coincident splats
still has one answer), and each cluster is replaced by one Gaussian that **matches the cluster's
moments**:

* **mass** `Σ alpha · sqrt(det Sigma)` — the integrated opacity, up to a `(2π)^{3/2}` that cancels;
* **mean** the mass-weighted centroid;
* **second moment** the mass-weighted covariance *about that centroid*, which is each member's own
  covariance **plus** its displacement — the parallel-axis term. Leaving that out is the classic
  mistake and yields a coarse level of tiny dots with holes between them;
* **colour** the mass-weighted mean.

The merged alpha is then chosen so `alpha · sqrt(det Sigma) = mass`, clamped at 1. At runtime the
budget picks a **level**, not a set of splats.

## 4. The interaction contract

Most of this table is still "does not interact". Writing that down is the point: an unstated
contract is how a research prototype becomes an unmaintainable feature.

| Surface | Today | Why, and what it would take |
|---|---|---|
| **Depth buffer** | Tested, never written. | A splat has no surface, so there is no depth to write. It can be depth-tested against the opaque G-buffer if drawn after opaque geometry — the prototype's `gl_Position.z` carries the real NDC depth for exactly that. Splats cannot occlude each other through depth; only the sort orders them. |
| **Deferred lighting** | Not integrated, and cannot be. | The colour in a splat is **baked radiance** from the capture, not a BRDF input. It has no normal, roughness or albedo to write into the G-buffer. A splat cloud must be composited *after* lighting, in the transparency phase. |
| **Shadows (cast)** | No. | Nothing to rasterise into a CSM or VSM page. Casting needs a separately authored opaque proxy mesh, which is a second asset with its own authoring cost. |
| **Shadows (receive)** | No, and it would be wrong. | The capture's own lighting is already in the colour. Applying engine shadows on top double-darkens. |
| **Reflection probes / IBL** | No. | The probe bake path renders meshes through the deferred pass; splats are not in it. And a splat receives no IBL, for the same baked-radiance reason. |
| **Collision (Jolt)** | No. | No surface, no triangles. A splat cloud is decoration; anything the player touches needs a proxy body. |
| **Scene serialization** | None. | The honest cost of "make it a feature": a `SplatCloudComponent` pulls in the whole cross-binding list in `CLAUDE.md` — `AllComponents`, save-game capture/restore *and* a hand-written `Serialize` overload, Lua registration, the editor inspector and Add Component menu, and a scene-YAML block (the component holds a `Ref<T>`, so codegen skips it). |
| **Asset registry** | Deliberately outside it. | `.ply` is **already** registered as `AssetType::MeshSource`, so a splat PLY dropped in the Content Browser today is read by assimp as a point mesh and silently loses everything but `x y z`. Two importers cannot share one extension; a real feature has to discriminate on file *content* (an `f_dc_0` property). See `notes-editor-and-assets.md`. |
| **OpenGL 4.6** | Works, ordering and raster both. | This is what every measurement and PNG below is. |
| **Vulkan** | Shaders compile for `vulkan1.2`; the *binding model* does not port as written. | ADR 0010/0011: the Vulkan backend is heap-bindless only. The prototype binds five SSBOs and two UBOs to fixed binding points, which is precisely the model that backend does not have. An RHI-neutral splat pass has to go through the neutral resource/binding-address model, and the indirect draw has to become an RHI concept. A real port, not a recompile. |

## 5. Measurements

All numbers are from this workstation (RTX 4090, Windows 11, clang-cl) on 2026-09-04. They are
**not** CI gates — no assertion depends on any of them
(`oloengine-perf-tests-are-dev-workstation-only`). Re-derive before quoting them anywhere else.

### 5.1 Memory

| | 4,096-splat fixture | per splat |
|---|---|---|
| Source PLY (62 float properties) | 1,017,407 B | 248 B |
| Runtime GPU record | 131,072 B | 32 B |
| Dropped at import (`nx ny nz`, `f_rest_0..44`) | 786,432 B | 192 B |
| Draw-order + sort-key buffers, per view | 32,768 B | 8 B |
| Whole LOD chain (4096 + 1024 + 256 + 64) | 174,080 B | 1.33× the base level |

**7.8× smaller than the source.** The LOD chain adds a third on top, which is the geometric series
`1 + 1/4 + 1/16 + …` and is the price of the levels in §5.5. Extrapolated, a 2 M-splat scan is a
496 MB PLY that becomes 64 MB of records, 85 MB with its chain, plus 16 MB of per-view sort state.

Memory is still where a splat cloud is *worst* against a mesh asset, and the ratio hides it: a mesh
shares one texture across thousands of triangles and streams by mip, while splat memory is linear in
captured detail with nothing to share.

### 5.2 The per-view ordering pass: CPU reference against the GPU pass

The CPU column is Release, single-threaded, mean of 20 iterations, median of three runs on an idle
machine, measured with a standalone `-O2` probe over the same translation units — the Debug suite's
own numbers are 5–10× higher because `/MDd` checked iterators serialise every `std::vector` access.
The GPU column is `GL_TIME_ELAPSED` around the whole pass (cull + LOD + sort), minimum of four
samples, in the Debug test binary — host build configuration does not change GPU work.

| splats | drawn | CPU whole pass | GPU whole pass | speed-up |
|---:|---:|---:|---:|---:|
| 4,096 | 3,043 | 0.14 ms | **0.085 ms** | 1.6× |
| 100,000 | 74,431 | 2.60 ms | **0.262 ms** | 9.9× |
| 500,000 | 372,165 | 16.55 ms | **0.506 ms** | 33× |
| 2,000,000 | 1,488,977 | 155.3 ms | **4.683 ms** | 33× |

**This is the number that reversed the decision.** A 16.7 ms frame at 60 Hz has everything else in
the engine in it too; giving the ordering a fifth of it bought 120–150 k visible splats on the CPU
and buys well past 2 M on the GPU. Published 3DGS captures of a single room are 1–6 M splats, so the
sizes people actually publish went from an order of magnitude out of reach to comfortably inside the
budget.

Two details worth keeping. **The sort was never the expensive half of the CPU pass** — at 500 k it
was 5 ms of 16.5; the other 11 ms was one covariance unpack, one dot product and six plane tests per
splat, which is exactly the embarrassingly parallel work a compute dispatch exists for, and it is
why moving the *whole* pass won more than moving the sort would have. And **the CPU radix sort was
never measurably faster than `std::stable_sort`**: across six runs they traded places at every size.
The radix formulation earned its place only by being the one that ports; a CPU-only implementation
should use `std::stable_sort`.

### 5.3 The raster pass against an opaque control

Measured with `GL_TIME_ELAPSED`, minimum of four interleaved samples per configuration. Both parts
of that matter and both come from a real mismeasurement here: A-then-B drifts far enough on this box
to invert a comparison, and a first run reported 10.3 ms where a later run reported 4.3 ms for the
identical draw, because the GPU had not reached its clock state. The control is
`SplatSpike_OpaqueBaseline.glsl`: it reads the same records through the same order buffer, so both
passes rasterise the identical quads at identical positions and sizes, then does none of the things
that make a splat a splat — no per-fragment Gaussian, no blending, depth-tested and depth-writing.

| splats drawn | splat pass | opaque control | ratio |
|---:|---:|---:|---:|
| 4,066 | 0.123 ms | 0.056 ms | 2.2× |
| 99,208 | 0.945 ms | 0.546 ms | 1.7× |
| 496,002 | 6.000 ms | 3.416 ms | 1.8× |

The absolute times move by up to 2× between runs with clock state; the **ratio** stayed between 1.7×
and 1.8× at both large sizes across four runs, so that is the number to trust. **Blending plus the
per-fragment Gaussian costs about 1.8× an equivalent opaque pass** — affordable, and now the
*dominant* cost, since ordering fell to 0.5 ms. Splat cost is overdraw cost: at 500 k splats the
cloud covers a 1280×720 frame roughly 160 times over, and overdraw *grows* as the camera approaches,
the opposite of a mesh.

### 5.4 Quality

`Splat_Front.png`, `Splat_Corner.png`, `Splat_Top.png` and `Splat_Close.png` are the fixture from
four poses. They read correctly: the disc facing the camera is a filled ellipse while the two
edge-on discs are thin lines (so the anisotropic covariance survives the 32-byte packing), the three
discs cut each other along the right half-spaces, and the translucent shell composites over all of
them. `Splat_Corner_ReversedOrder.png` is the same pose drawn front-to-back — every occlusion
inverts, and the frame moves 3.9/255 mean absolute difference, which is what makes the sort's
necessity visible rather than asserted.

`Splat_Corner_GpuOrdered.png` is the same pose ordered by the GPU pass and drawn indirectly. It
matches the CPU-ordered frame to under 0.5/255, which is the end-to-end check that the index parity
in §3.1 actually reaches the screen.

### 5.5 Selection against merging, at matched splat counts

Both LOD schemes captured from the Corner pose, classified by the same code. The full frame paints
103,956 shell pixels and 49,288 disc pixels.

| splats | scheme | shell px | disc px | mean abs difference vs full |
|---:|---|---:|---:|---:|
| 1,024 | selection budget | 2,074 | 41,200 | 10.056 / 255 |
| 1,024 | **merged level** | **106,865** | **42,691** | **3.022 / 255** |
| 256 | selection budget | 2,231 | 19,264 | 11.006 / 255 |
| 256 | **merged level** | **112,938** | **23,428** | **6.430 / 255** |

**Selection deletes the faint diffuse mass and keeps the bright detail**: at a quarter of the cloud
the shell loses 98 % of its pixels while the discs keep 84 %, and what is left at 256 splats is a
skeleton rather than a lower-detail scene. **Merging keeps both** — the shell even grows, because a
coarse splat spreads the same mass over a wider footprint — and at a quarter of the splats it is
three times closer to the full frame than selection is.

Mass ratios along the chain, measured directly rather than inferred from pixels: **0.80, 0.76, 0.76**
of the base level at 1024, 256 and 64 splats. The shortfall is the opacity clamp — a merged splat
cannot be more than fully opaque, so a cluster that was already dense loses a little — and it is
one-sided by construction: `EveryLevelCarriesTheSameMass` allows a shortfall and forbids a gain,
because a scene that got *brighter* as it coarsened would be a sign error rather than a rounding
loss.

One honest cost, visible in the table: **merging desaturates.** A coarse splat carries the
mass-weighted mean colour of its cluster, so once clusters span the boundary between a red disc and
the white shell the result greys out, and the classifier counts those pixels as shell. Total painted
area is preserved — which is what merging promises — while saturation is not. A production
implementation would cluster with a colour term in the metric, not only position.

## 6. Decision and what remains

**Proceed.** Gaussian splats are a viable asset class for this engine, on these terms:

1. **The per-view ordering runs on the GPU.** The CPU implementation stays as the parity reference
   and as documentation of the algorithm; it is not a supported runtime path at scan scale.
2. **LOD is built offline by merging.** The selection budget in `ViewSettings::MaxSplats` remains
   only as the negative control the tests pin; new work must not reach for it as a LOD knob.
3. **The contract in §4 does not change quietly.** A PR that gives a splat cloud shadows, collision
   or probe capture amends this ADR first.

Still unbuilt, and each is integration work rather than an open question:

- **`SplatCloudComponent` and its cross-binding touch-points** — the `CLAUDE.md` table in full, plus
  a scene-YAML block written by hand because the component holds a `Ref<T>`.
- **Content-sniffing PLY import dispatch** — `.ply` already means `MeshSource`, so the importer has
  to discriminate on an `f_dc_0` property rather than the extension.
- **The RHI-neutral Vulkan pass** — five SSBOs, two UBOs and an indirect draw, all currently on fixed
  GL binding points that the heap-bindless backend does not have.

These are deliberately not filed as issues yet: they are one coherent piece of integration work that
should be scoped together once someone commits to shipping the feature, and three separate issues in
front of the picker would invite starting in the middle.

## Appendix: how the two preconditions were closed

Kept because the reasoning is the reusable part.

**#1038, GPU ordering.** The blocker was never "is a GPU sort possible" — it was "can a GPU sort be
*trusted* against the reference". Making the sort key a total order over (depth, index) turned that
from a testing problem into an arithmetic one: with exactly one correct answer, parity is an equality
assertion. Everything else followed, including the freedom to use an unstable sort and an unordered
atomic compaction.

**#1039, merge LOD.** The blocker was recognising that no *ranking function* fixes selection. The
first implementation ranked on screen area × alpha, which is a reasonable-sounding heuristic and
loses the diffuse mass; so would ranking on alpha, or on distance, or on any other per-splat score.
The property that matters — the total integrated opacity of a region — is not a property any single
splat has, so it cannot be preserved by choosing among them. That is what forced the move to
moment-matching, and it is why §5.5's assertion is one-sided about mass rather than symmetric.

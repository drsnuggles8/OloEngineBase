# Follow cameras, character controllers, and who a scene query can actually see

Rules from building the reusable player + camera rig (issue #645, #897, #607, #438). Read before touching `CameraRigComponent`, `PlayerRigSystem`, character-controller bodies, entity-excluding raycasts, mouse/keyboard input in fixed-step systems, or any vehicle's forward/right convention.

## Rules

1. **Set user data on any physics body added by a path other than `JoltBody`.** Entity-level filters (`EntityExclusionBodyFilter::ShouldCollideLocked`) resolve entities through `JPH::Body::GetUserData()` and treat `0` as "allow". The `CharacterVirtual` inner body had none, so `RayCastInfo::m_ExcludedEntities` could never exclude a character controller (a spring arm collapsed to minimum; `PerceptionSystem`'s own-body exclusion was a no-op). The UUID is stamped right after `new JPH::CharacterVirtual(...)`. [Details](follow-camera-and-character-query-seams-details.md#1-a-jolt-charactervirtuals-inner-body-carries-no-user-data--so-every-uuid-keyed-filter-silently-ignores-it)
2. **Test the exclusion in a real physics world.** A kernel test of the pull-in math passes with the bug present; assert "with only the player in front of the camera, the boom stays at full length". [Details](follow-camera-and-character-query-seams-details.md#1-a-jolt-charactervirtuals-inner-body-carries-no-user-data--so-every-uuid-keyed-filter-silently-ignores-it)
3. **Run the follow camera after physics and transform propagation, and the rig input before `PhysicsKick`.** Pin it as scheduler edges (`DependsOn("CameraRig", "PhysicsFence")`, `…"PropagateTransforms"`, and every post-propagate transform writer such as `Navigation`, `BoidMovement`; see parallelizable-mover-systems.md), plus a moving-target functional test asserting the offset every frame within a tolerance tighter than one tick's travel (2 cm at 3 m/s and 1/60 s). A static position check passes with the edges missing. [Details](follow-camera-and-character-query-seams-details.md#2-a-follow-camera-must-run-last-and-a-position-check-will-not-tell-you-it-doesnt)
4. **Consume a pointer-derived look delta exactly once per rendered frame, never once per fixed tick, and never multiply it by `dt`.** Read the delta and rebase the stored position; a frame with no tick leaves the delta outstanding. Walk speed always takes `dt`. [Details](follow-camera-and-character-query-seams-details.md#3-mouse-look-is-a-displacement-movement-is-a-rate)
5. **Guard a device-derived look delta against teleports: bound it in degrees of implied rotation (delta x sensitivity), drop the sample rather than clamping, and rebase the stored position even on a rejected sample.** Window minimize/restore/move/resize jump the pointer without a cursor-mode change (`WindowFocus` has no GLFW callback). Apply this to the device path only; script- or network-driven look input is taken at its word. [Details](follow-camera-and-character-query-seams-details.md#deriving-a-delta-from-an-absolute-position-needs-a-teleport-guard)
6. **Never call `Input::IsKeyJustPressed` in a fixed-step system (`SimulateRuntimeStep`).** It is snapshotted once per rendered frame (`Input::Update`), so it is true on every tick of that frame and a jump fires N times. Derive the edge from the level (`IsKeyPressed` plus stored previous state). [Details](follow-camera-and-character-query-seams-details.md#deriving-a-delta-from-an-absolute-position-needs-a-teleport-guard)
7. **Smooth with `1 - exp(-dt/tau)`, never a fixed per-frame lerp factor.** It composes exactly, so one step at `dt` equals two at `dt/2`, which is directly assertable. [Details](follow-camera-and-character-query-seams-details.md#deriving-a-delta-from-an-absolute-position-needs-a-teleport-guard)
8. **Apply an injected value that a consumer integrates as a never-reverted delta, not a temporary override.** `olo_input_inject`'s absolute `move` is reverted when the plan drains, so integrated deltas cancel (`dYaw = 0.000`, pitch pinned at `MaxPitchDeg`); latching longer (`holdFrames`) does not help. Use `SyntheticInput`'s accumulated cursor offset and the `mouseDelta` action; overrides are only for consumers reading absolutely (ImGui widgets, gizmo drags), and the two paths stay separate (issue #607). [Details](follow-camera-and-character-query-seams-details.md#a-delta-consumer-cannot-be-driven-by-an-absolute-override-that-gets-reverted)
9. **Prefer a parameter over a mode enum when one subsumes the other.** First person is third person with a zero-length boom; keep one component and two preset field sets in one preset header. Express genuine body differences as independent booleans (`m_YawBodyWithLook`, `m_FaceMoveDirection`) and pin their mutual exclusivity in a preset test (one wins when both are set). [Details](follow-camera-and-character-query-seams-details.md#4-prefer-a-parameter-over-a-mode-enum--and-check-whether-one-already-subsumes-the-other)
10. **Ship a UUID-wired pair of entities as a demo scene, not a prefab.** A prefab has one root and fresh UUIDs on instantiation, so a camera's target reference would dangle; ship the single-entity half as a prefab and say so in the guide. [Details](follow-camera-and-character-query-seams-details.md#5-a-two-entity-rig-cannot-be-one-prefab)
11. **Get a target's facing from `EntityFacing::ConventionFor(entity)` (`Scene/EntityFacing.h`), and yaw from `EntityFacing::YawDegrees(rotation, convention)`.** `BoatComponent` / `VehicleComponent` / `AircraftComponent` mean `+Z` forward, everything else `-Z`; add any new force-model vehicle to that roster. Keep the yaw math in one place (`PlayerRigSystem` delegates). [Details](follow-camera-and-character-query-seams-details.md#6-the-targets-facing-is-not-one-thing--ask-which-convention-it-uses-issue-897)
12. **Use `CameraRigComponent::m_TargetForward` (`Auto` / `MinusZ` / `PlusZ`) only when a scene's target carries no vehicle component for derivation to see, and Reject (not Clamp) corrupt values on load.** A bad value falls back to `Auto`. [Details](follow-camera-and-character-query-seams-details.md#6-the-targets-facing-is-not-one-thing--ask-which-convention-it-uses-issue-897)
13. **Test camera framing by the sign of the offset, `(camera - target) · targetForward < 0`, not by distance.** A rig pointed 180 degrees wrong still sits one boom length away and looks deliberate. [Details](follow-camera-and-character-query-seams-details.md#6-the-targets-facing-is-not-one-thing--ask-which-convention-it-uses-issue-897)
14. **Treat starboard as `-X` for a `+Z`-forward body (right == forward x up, right-handed, `+Y` up); `+X` is port.** #438 had it backwards in `BoatSystem` rudder torque, `AircraftSystem` roll/yaw and `JoltScene` wheel layout (wheel 0 "FL" at `-halfTrack`, `m_LeftRightSplit`); tests measured magnitudes and missed the sign. Convention errors hide in symmetric consumers like `BoatSystem`'s `rightFlat` drag decomposition. [Details](follow-camera-and-character-query-seams-details.md#the-same-mistake-one-layer-down-starboard-is--x-for-a-z-forward-body)

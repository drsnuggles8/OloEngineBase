# Cross-checking a per-vendor golden baseline set

Read before baking a new `assets/tests/{golden,visual}/<vendor>/` set, before trusting an existing one, and before concluding a cross-vendor pixel delta is "just driver variance" (issues #734, #735, #754). A golden keeps the nightly green but does not prove the render is correct, and a per-vendor set then validates itself.

## Rules

1. **Treat RMSE as a screening tool, never a verdict.** A small RMSE means portability, not correctness (two vendors running the same wrong shader agree); a large RMSE can come from depth ties and visibility-threshold float comparisons. [Details](vendor-golden-baseline-crosscheck-details.md#1-why-rmse-cannot-settle-it-in-both-directions)
2. **Measure the noise floor first.** Capture the reference vendor twice into two scratch directories and diff those; the floor is per-test (some are byte-identical, some move by 158/255). A cross-vendor delta at or below it carries no information. [Details](vendor-golden-baseline-crosscheck-details.md#2-measure-the-noise-floor-first--before-attributing-anything)
3. **Separate vendor difference from temporal drift.** Compare fresh N1 vs N2 (noise), N1 vs committed shared set (drift), N1 vs committed vendor set (vendor + drift), and vendor set vs shared set. A drift row above the floor means the headline number says little about the vendor. [Details](vendor-golden-baseline-crosscheck-details.md#3-separate-vendor-difference-from-temporal-drift)
4. **Check the fixture did not move since the bake.** Diff the test `.cpp` between the bake commit and HEAD for scene, camera or threshold changes: `git diff <bake-commit> HEAD -- <the test .cpp> | grep -E '^[+-]' | grep -vE '^[+-]{3}|^[+-]\s*//'`. [Details](vendor-golden-baseline-crosscheck-details.md#3-separate-vendor-difference-from-temporal-drift)
5. **Use the property audit as the correctness oracle.** `OloEngine/tests/Rendering/PropertyTests/GoldenBaselineAuditTest.cpp` (L9) runs the #734 guards over every committed set (shared and each vendor subdirectory, discovered) with no GPU. A guard failing on a vendor baseline means the recording froze a defect: rebake plus a bug, not a threshold change. [Details](vendor-golden-baseline-crosscheck-details.md#4-the-property-audit-is-the-oracle-that-actually-answers-is-it-correct)
6. **Keep audit and parity separate.** The audit asks "is this recording of a correct frame?"; `VendorSetsAgreeWithTheSharedSet` asks "do the vendors agree?". A shared-code defect passes the second and fails the first. The audit does not mirror the splatmap's RGBA16F intermediate guard, which an 8-bit PNG cannot carry. [Details](vendor-golden-baseline-crosscheck-details.md#4-the-property-audit-is-the-oracle-that-actually-answers-is-it-correct)
7. **Look at a per-pixel max-delta heatmap before classifying a residual.** Thin lines converging at the horizon are the `InfiniteGrid` depth tie; isolated specks in the sky are stars at the threshold; a broad smooth region is lighting, fog or tone mapping and is not benign. The grid pattern says which feature moved, never why: in #735 it was stale-baseline drift, and only the section 3 decomposition separates them. [Details](vendor-golden-baseline-crosscheck-details.md#5-localize-a-residual-geometrically-before-classifying-it)
8. **Compare star fields as threshold masks, as sets.** Sweep the threshold and include a control shifting one mask by a single texel (88% agreement). [Details](vendor-golden-baseline-crosscheck-details.md#5-localize-a-residual-geometrically-before-classifying-it)
9. **Use CLI flags, `=value` form only.** `--olo-golden-vendor=<name>` and `--olo-golden-rebase`, parsed in `OloEngine/tests/TestOptions.cpp`. The `OLOENGINE_GOLDEN_VENDOR` / `OLOENGINE_GOLDEN_REBASE` env vars are removed, and `--olo-golden-vendor amd` (space) is a hard error so a rebase cannot overwrite the shared baselines. [Details](vendor-golden-baseline-crosscheck-details.md#6-mechanism-reference--the-things-that-are-easy-to-get-wrong)
10. **Remember five suites scope by vendor, each with its own copy of the path.** `GoldenImageTests.cpp::GoldenBaselineDir` (`assets/tests/golden[/<vendor>]`), and `assets/tests/visual[/<vendor>]` in `AtmosphereVisualEvidenceTest.cpp`, `DriftWeatherVisualEvidenceTest.cpp`, `FoliageWindEvidenceTest.cpp` and `FoliageInteractionEvidenceTest.cpp`. The value is whitelisted at parse time (`RequirePlainPathComponent`); `--olo-perf-machine` is a third such path component. [Details](vendor-golden-baseline-crosscheck-details.md#6-mechanism-reference--the-things-that-are-easy-to-get-wrong)
11. **Run goldens from `<repo>/OloEditor`.** Baseline paths are spelled `assets/...`; the repo root makes every golden "missing". [Details](vendor-golden-baseline-crosscheck-details.md#6-mechanism-reference--the-things-that-are-easy-to-get-wrong)
12. **Never commit `<name>.actual.png` / `<name>.diff.png`.** They are generated L10 escalation artefacts, `.gitignore`d. [Details](vendor-golden-baseline-crosscheck-details.md#6-mechanism-reference--the-things-that-are-easy-to-get-wrong)
13. **A missing vendor baseline is a hard FAIL, not a skip.** `CompareOrBootstrap` and `AtmosphereVisualEvidenceTest::Capture` fail on a missing set; `cross-vendor.yml` passes `--olo-golden-vendor=llvmpipe` with no such directory and is green, likely via the GPU gate (not confirmed). Do not assume a missing vendor directory is benign. [Details](vendor-golden-baseline-crosscheck-details.md#6-mechanism-reference--the-things-that-are-easy-to-get-wrong)
14. **Clean up empty vendor directories after a scratch run.** `--olo-golden-vendor=<v>` creates `golden/<v>/` via `fs::create_directories` even when the run fails; `GoldenBaselineAuditTest` treats an empty one as "not a baseline set". [Details](vendor-golden-baseline-crosscheck-details.md#6-mechanism-reference--the-things-that-are-easy-to-get-wrong)
15. **Never rebake into the shared set to close a cross-check.** Capture into a scratch vendor directory (`--olo-golden-vendor=nvidia-crosscheck-run1`) and delete it. Never `git add -A` after a suite run: it can dirty tracked goldens under `assets/tests/visual/`. [Details](vendor-golden-baseline-crosscheck-details.md#7-never-rebake-into-the-shared-set-to-close-a-cross-check)
16. **Keep per-vendor scoping and also cross-compare the sets.** Per-vendor baselines give tight self-comparison; shared ones give conformance but spend threshold on the vendor term. `GoldenBaselineAudit.VendorSetsAgreeWithTheSharedSet` has two tiers: 4 renderer goldens by pixel (RMSE < `kRmsePassBelow`, max delta <= 2) and 13 Atmosphere captures by derived per-band luma delta < 2.0 plus an RMSE <= 8.0 backstop. [Details](vendor-golden-baseline-crosscheck-details.md#what-to-do-about-it--keep-scoping-and-cross-compare)
17. **If either self-applied gate moves, move its copy in the audit.** The RMSE bars equal `kRmsePassBelow` and `kGoldenRmseThreshold`, which are copies by convention, not references. [Details](vendor-golden-baseline-crosscheck-details.md#what-to-do-about-it--keep-scoping-and-cross-compare)
18. **Re-run the audit on a freshly baked set from each vendor.** A cross-check against an old recording cannot see divergence introduced on that vendor afterwards. The shared Atmosphere set still needs a rebake at HEAD (0.87-2.60 drift). [Details](vendor-golden-baseline-crosscheck-details.md#the-one-thing-this-cross-check-could-not-do)
19. **Rebake a golden's vendor twin in the same PR as the golden.** The PR checks compare only the neutral image, so a stale `amd/` twin turns the nightly red after the merge; the `vendor-golden-twins` pre-commit hook fails the PR until the twin changes or is waived. Rebake it from the branch with `gh workflow run gpu-conformance-amd.yml --ref <branch> -f golden_rebase=true` ([runner doc](../ops/self-hosted-gpu-runner.md#rebaking-the-amd-twins-from-a-branch)). [Details](vendor-golden-baseline-crosscheck-details.md#9-a-neutral-rebake-leaves-the-vendor-twin-stale)

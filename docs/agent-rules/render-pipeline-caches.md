# Render-pipeline caches must invalidate on every reconfigure, not just on a fingerprint change

Rules for anyone adding a process-wide cache to `Renderer3D::s_Data` (the `RenderPipeline`, the `RenderGraph`, the `TransientPool`, or anything with their lifetime), or a pass whose existence depends on a setting. In the test binary there is one instance shared by every test (issues #530, #563, #771, #595).

## Rules

1. **Invalidate a cache that depends on the blackboard / imported-resource maps by the same event that wipes them, not only when the inputs it hashes change.** `ResetTopology()` wipes the blackboard, so the second `RenderingPath::Deferred` entry in one process short-circuited `PopulateBlackboard` and culled the whole graph to a blank frame with no GL error (#530). [Details](render-pipeline-caches-details.md#the-trap)
2. **Hash `RenderGraph::GetTopologyGeneration()` into any per-frame cache key (as `FrameGraphDeclarationConfig::TopologyGeneration` does) instead of calling `InvalidateBlackboardCache()` at each settings site.** The counter is bumped by every `ResetTopology()` / `Shutdown()` and is process-wide since #1333, so even a future reconfigure path that forgets an explicit hook self-invalidates. [Details](render-pipeline-caches-details.md#the-rule)
3. **Evict the `TransientPool` whenever any graph node's framebuffer actually resized, not only when the display dimensions changed.** `RenderGraph::Resize` clears it when `dimensionsChanged || anyNode resized` (compares `GetFramebufferSpecification()` before/after `ResizeFramebuffer`); a genuinely idle resize must not clear it. [Details](render-pipeline-caches-details.md#the-rule-1)
4. **Also evict the pool in `RenderPipeline::PopulateBlackboard`'s FSR1 scene-band resize block, right after `ScenePass->ResizeFramebuffer`.** A runtime `Upscale` toggle changes the band without a window resize and never reaches `RenderGraph::Resize`; stale transients otherwise render black for ~2 frames (#563). For any transient sized by something other than display resolution (render scale, half-res AO band, cascade size), ask what changes that size and whether the pool is evicted. [Details](render-pipeline-caches-details.md#the-rule-1)
5. **Key every per-frame consumer of a topology-deciding setting off the value the graph was built with, not the pending one.** `ActiveAOTechnique` picks `SSAOPass` or `GTAOPass` at topology-build time; `RenderPipeline`'s AO gates (the `AOBuffer` declaration, the SSAO/GTAO scratch declarations, `AOApplyPass::SetEnabled`) read `data.ActiveGraphAOTechnique`, so an unapplied change degrades to "no AO" instead of a black frame. [Details](render-pipeline-caches-details.md#the-rule-2)
6. **Call `Renderer3D::ApplyRendererSettings()` after setting a technique field (including in tests).** Without it the topology and the per-frame hook disagree indefinitely; `olo_render_toggle_pass` in `McpTools.cpp` and issue #533 were earlier victims. [Details](render-pipeline-caches-details.md#the-trap-issue-771)
7. **Publish the neutral element on every path where a producer does not produce, using `Passes/AOTargetIdentity.h::PublishAOTargetAsFullyVisible`.** For multiplicative modulation (AO, shadow mask, fog transmittance) zero is the maximum-effect end, and fresh zeroed storage is exactly that. `SSAORenderPass` clears only its own scratch targets after its early returns, so that did not protect `AOBuffer`. [Details](render-pipeline-caches-details.md#the-rule-2)
8. **Gate both ends of a producer/consumer seam from the same value.** Producers bail out on their own `m_Settings.ActiveAOTechnique`, so feeding them the requested technique while the consumer reads the graph's reproduces the black frame with roles swapped; `RenderPipeline` hands both the graph's technique. [Details](render-pipeline-caches-details.md#the-rule-2)
9. **Treat "`OLO_RG_POISON_TRANSIENTS=1` fixes it but `OLO_RG_DISABLE_ALIASING=1` does not" as a diagnosis: some consumer samples storage nobody wrote this frame.** Check the `RenderGraph AO/Post order:` trace and the submission plan (`GTAO=n/a`) to confirm the pass is in the plan before debugging its contents. [Details](render-pipeline-caches-details.md#the-trap-issue-771)
10. **Use a producer's value floor as an assertion.** `GTAO.comp` clamps visibility to `[0.03, 1.0]`, so an AO texel of exactly 0 reaching the apply pass is unwritten storage. [Details](render-pipeline-caches-details.md#the-rule-2)
11. **Log every early return in a pass `Execute` (rate-limited, naming the guard), and publish the no-occlusion identity before it.** All four `GTAORenderPass::Execute` early returns were silent and had to be found by bisecting suite order. [Details](render-pipeline-caches-details.md#the-rule-2)
12. **Never rely on `RenderGraphNode::OnReset()`; it has zero call sites.** Its ~38 overrides are dead. Pass objects persist across `ResetTopology()` (only `RenderPipeline::Setup()` destroys them), so re-resolve every RG handle from the live graph inside `Execute()` each frame (`context.ResolveTexture(...)`, `context.ResolveFramebuffer(...)`), or wire a real call site into `BuildRenderPipelineGraph` / `ResetTopology` first. [Details](render-pipeline-caches-details.md#pass-objects-survive-a-topology-reset--but-rendergraphnodeonreset-is-a-dead-hook-595)

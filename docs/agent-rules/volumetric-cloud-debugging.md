# Debugging a volumetric cloud field that renders as a "uniform veil"

Eight different causes produce the same "uniform veil / no cloud structure" symptom in volumetric
cloud and fog features (origin: issues #633, #723, #987). Read this before concluding which cause you
have, and before verifying any self-shadowing feature.

## Rules

1. **Capture the intermediate buffer first, before any binary-search debug-colour loop.** `olo_render_capture_target` on the producer (e.g. `VolumetricShadowVolume`) shows whether the data exists and has structure, independent of every multiplier downstream. [Details](volumetric-cloud-debugging-details.md#the-eighth-cause-the-term-you-changed-is-not-the-term-the-pixel-shows)
2. **Check that every downstream consumer's candidate ladder includes the new pass output.** With Fog and Precipitation disabled, later passes (ChromAb to Final) fell back past `CloudsColor`; `CloudsRaw` had content while the final frame did not (glsl-shaders.md §9). [Details](volumetric-cloud-debugging-details.md#the-four-look-alike-causes-all-were-real-all-needed-separate-fixes)
3. **Check that every `remap(x, lo, hi, ...)` low edge lies inside the operand's real range.** A `lo` provably below `min(x)` is a no-op (the Nubis base shape needed the erosion floor `fbm * 0.85`). [Details](volumetric-cloud-debugging-details.md#the-four-look-alike-causes-all-were-real-all-needed-separate-fixes)
4. **Normalise procedural input textures against their own measured min/max, never an assumed mean.** Probe the inputs on the GPU (`o_Color = vec4(weather.r, noise.r, fbm, 1)`) before tuning the math that consumes them. [Details](volumetric-cloud-debugging-details.md#the-four-look-alike-causes-all-were-real-all-needed-separate-fixes)
5. **Compare feature size against the visible layer extent before calling the field broken.** `visible layer extent ≈ 2·tan(fov/2)·(layerHeight − cameraHeight)`; the editor camera FOV is 30°, so scales tuned there read twice as large at a 60° runtime FOV. [Details](volumetric-cloud-debugging-details.md#the-four-look-alike-causes-all-were-real-all-needed-separate-fixes)
6. **A test that drives the weather director must snapshot/restore all four settings structs (fog, wind, precipitation, snow) and reset the cloudscape render state in TearDown.** `WeatherSystem::ApplyImmediate/Tick` writes process-global Renderer3D settings that the `RendererAttachedTest` snapshot does not cover; symptom is other visual tests failing only in the full suite. [Details](volumetric-cloud-debugging-details.md#the-fifth-cause-found-in-the-full-suite-not-the-live-editor)
7. **A visual-evidence fixture must call `Renderer3D::ApplyRendererSettings()` after `EnableRendering`, and goldens must be rebased in that state.** A pristine test process never applies settings (#534 boot divergence), so standalone rebases pin the prepass-off state. [Details](volumetric-cloud-debugging-details.md#the-sixth-cause-also-found-in-the-full-suite--the-reverse-leak)
8. **Put only spatially varying density in a light-path integral.** A spatially constant term (e.g. `FogSettings::AbsorptionCoefficient`) contributes `exp(-k·L)` with `L` the fitted-volume path length, a veil that changes whenever the volume is refitted; it belongs in the view-ray integration. `VolumetricShadow_Generate.comp` integrates `combinedDensity` and deliberately not the floor. Probe: rotate the light 90° and re-capture; real occlusion moves, a constant veil only changes magnitude. [Details](volumetric-cloud-debugging-details.md#the-seventh-cause-a-spatially-constant-term-inside-a-light-path-integral)
9. **Before asking why your term is zero, check whether another radiance term dominates the composite.** The ambient term (`u_CloudAmbient * mix(0.25, 0.75, heightFrac)`) is unshadowed; the phase function and a saturated `cloudLightOpticalDepth` (1400 m cone, optical depth ~20 at stock `Density` 1.0-1.6) also hide self-shadowing. [Details](volumetric-cloud-debugging-details.md#the-eighth-cause-the-term-you-changed-is-not-the-term-the-pixel-shows)
10. **Do not rebalance the look to make a feature visible; author the test in the isolating configuration and report the stock magnitude.** Self-shadowing is visible only for moderate density and a low sun (measured delta 0.16% at 60 deg, 17.0% at 12 deg), so a test that picks one sun angle can conclude anything. [Details](volumetric-cloud-debugging-details.md#the-eighth-cause-the-term-you-changed-is-not-the-term-the-pixel-shows)
11. **Verify a self-shadowing feature with a difference of differences, not a golden.** Capture feature off/on from a light-facing and an away-facing aspect and assert the shaded aspect loses more; this cancels driver, exposure, phase and sun colour (`VolumetricShadowVisualEvidenceTest` is the example). [Details](volumetric-cloud-debugging-details.md#telling-darker-from-directionally-darker)
12. **Work out which camera pose is lit before encoding "sun side" and "shadowed side" in a test.** Looking toward a low sun looks along the light path through the most medium, the darkest view; lit faces have the light behind the camera. [Details](volumetric-cloud-debugging-details.md#the-three-observation-traps)
13. **Reposition the editor camera before capturing pass-internal buffers.** `olo_render_capture_target` shows the editor viewport camera, not the `olo_screenshot` pose; use `olo_camera_set_pose` (pitch in DEGREES, negative = up). [Details](volumetric-cloud-debugging-details.md#the-three-observation-traps)
14. **Cold-restart the editor when an include-only shader edit does not change behaviour.** Hot-reload with `#include` staleness is unproven. [Details](volumetric-cloud-debugging-details.md#the-three-observation-traps)
15. **Use the MCP binary-search shader-debug loop for the unexplained case.** Unconditional debug colour at the top of `main()`, then after the early-out, then intermediates; each step is an on-disk edit + `olo_shader_reload` + `olo_render_capture_target {forceFrame:true}`. [Details](volumetric-cloud-debugging-details.md#the-technique-that-worked-use-it-first-not-last)
16. **Retune `kCloudExtinction` (CloudscapeCommon.glsl) in two files.** The CPU mirror in `CloudDensityMathTest.cpp` re-declares it literally. [Details](volumetric-cloud-debugging-details.md#residual-knowledge)
17. **Move the `cloudLightNearRange()` cap (1400 m or layer thickness) only knowing it moves both halves of the split light path.** The cone march owns `[0, near]`, the volumetric shadow map owns the rest; dropping the map stops the layer above the cap shadowing. [Details](volumetric-cloud-debugging-details.md#residual-knowledge)
18. **Keep the volumetric shadow volume free of a temporal term.** If jitter is ever added, make it a function of the cell, not the frame index. [Details](volumetric-cloud-debugging-details.md#residual-knowledge)
19. **Keep the artistic single-scatter albedo (~0.5) on the sun term.** In-scatter integrates to several times the sun intensity over a kilometre-scale medium. [Details](volumetric-cloud-debugging-details.md#residual-knowledge)
20. **Classify cloud depth conservatively: use the minimum of the 2x2 full-resolution depth footprint, and treat sky as exactly `1.0`.** Clamp coordinates for odd-sized viewports; a broad epsilon like `0.9999` misclassified terrain (ridge depth `0.999904` with a 1000 m far plane). Pin both in an `R32F` shader-unit contract, since RGBA8 cannot represent far depths. [Details](volumetric-cloud-debugging-details.md#a-different-signature-cloud-puffs-in-front-of-terrain)
